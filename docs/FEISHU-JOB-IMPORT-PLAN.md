# 飞书表格链接导入 RiLL 投递信息：实施方案

> 日期：2026-10-25（Asia/Shanghai）
>
> 状态：设计背景归档；实现与使用以 [飞书投递导入](FEISHU-IMPORT-DELIVERY.md) 为准。
>
> 基线：本地 RiLL 0.1.3 源码；实施时保留工作区已有修改，重新核对接口。
> 核心目标：用户提供飞书表格链接，RiLL 读取表格，理解不同人的字段和进度写法，将个人投递记录导入求职中心。

## 1. 产品目标与交付边界

### 1.1 用户最终获得的能力

在“求职中心”点击“从飞书导入”，粘贴链接；首次完成连接、核对自动识别的字段映射后，批量导入投递记录。再次导入同一数据源时复用映射，仅处理新增内容和有变化的内容。

“一键”指完成首次连接和映射后，点击一次即可导入符合已保存规则的新增记录；有歧义、覆盖冲突和表结构变化的记录进入待核对，不用每次重新配置整张表。

目标成功路径：

```text
飞书链接
  → 确认访问身份、文档类型和读取范围
  → 读取字段与记录
  → 自动映射 + 逐行识别
  → 首次预览 / 后续复用规则
  → 去重、冲突检查
  → 原子提交到 RiLL
  → 投递列表立即刷新，可查看来源与本次结果
```

### 1.2 首版必须包含

1. 输入链接，读取有访问权限的 Sheets 和独立 Base；用户给出的 Sheets 内嵌记录表必须在技术验证阶段单独验证，不能按普通单元格表假定成功。
2. 自动识别不同字段名、字段顺序，允许手动修正映射并按数据源保存。
3. 同一表格中逐行区分个人投递、明确待投、纯招聘信息、无法判断的内容。
4. 个人投递写入 `job_applications`；明确待投写入同表的 `preparing` 状态。
5. 导入前预览、重复导入去重、覆盖冲突处理、失败重试、取消和导入结果统计。
6. 保留来源、未映射字段与原始行；投递日期未知时不编造日期。
7. 无 AI 配置时，仍可通过规则与手动映射完成标准表格导入。

纯招聘信息默认列为“未导入：招聘信息”，允许用户明确选择“加入准备投递”；“写入信息库”的开关可作为后续扩展。首版完成标准不依赖改造 scout 写入链路。

这个边界保证核心交付是“链接 → 投递信息”，同时避免将整张公共招聘清单误记成用户已投递的岗位。

### 1.3 首版不包含

- 定时同步、双向同步、回写飞书、自动跟随源表删除本地记录。
- 根据面试日期自动创建日历事件；RiLL 当前邮箱排程有独立确认流程，应继续保持。
- 将 RiLL 改造成可任意增加显示列的通用表格产品；额外字段先放详情。
- 图片 OCR、图片颜色判定、仅凭删除线判断失败等视觉推断。
- 把 Kimi、Codex 或开发者本机的 webbridge 当作发布版必须安装的运行依赖。

## 3. 飞书连接与文档类型识别

### 3.1 链接结构与读取器探测

以下链接使用虚构资源标识：

```text
https://my.feishu.cn/sheets/exampleSpreadsheet
  ?sheet=exampleSheet
  &table=exampleTable
  &view=exampleView
```

设计阶段需要通过用户 OAuth 验证文档类型、字段和全范围记录，不能只依据网页标题。实际验证范围见 [连接验证说明](FEISHU-P0-VALIDATION.md)，私人文档链接与报告不纳入仓库。

`/sheets/` 路径不能独自决定读取器；`table/view` 参数提示需要探测内嵌记录表，但不能据此直接宣称它是独立 Base。也不能未经验证就把路径中的 token 当作 Base 的 `app_token`。

### 3.2 链接解析与读取器

统一解析为 `SourceDescriptor`，保留原始定位参数；通过有权限的元数据接口确认实际资源类型。

| 类型 | 读取路径 | 说明 |
|---|---|---|
| 普通 Sheets | 工作表元数据 → 按 A1 行范围分块读取 | 数据读取使用 Sheets 的相应数据接口，不能根据文档 URL 中的 v3 推断所有接口均为 v3 |
| 独立 Base | 应用/数据表元数据 → 字段 → 分页记录 | 使用真实 `field_id`、`record_id`；处理超链接、单选、多选、日期等字段类型 |
| Sheets 内嵌记录表 | 先解析父文档与实际记录表的关系，再调用已验证的读取器 | P0 必须验证该示例；解析不了时返回明确的不支持结果，不猜 token |
| Wiki 等包装链接 | 后续扩展 | 首版明确提示暂不支持，不能伪装成普通 Sheets |

拟使用的主要 API 路径：

```text
GET /open-apis/sheets/v3/spreadsheets/{token}/sheets/query
GET /open-apis/sheets/v2/spreadsheets/{token}/values/{range}

GET /open-apis/bitable/v1/apps/{app_token}
GET /open-apis/bitable/v1/apps/{app_token}/tables
GET /open-apis/bitable/v1/apps/{app_token}/tables/{table_id}/fields
GET /open-apis/bitable/v1/apps/{app_token}/tables/{table_id}/records
```

以上为接口族设计；精确权限、视图参数和内嵌表关联方式必须根据当时接口文档与真实响应在 P0 固化，记录验证结果。

### 3.3 授权方案：浏览器登录不等于 API 授权

产品采用用户身份的授权读取，访问范围取决于应用获批权限和用户对文档的实际权限。公开分享链接也不等于免认证 API。

连接模块暴露 `connect / getAccessToken / refresh / disconnect`，导入流程只依赖接口，不依赖特定 OAuth UI。

推荐落地顺序：

1. **P0 个人验证版**：使用用户自己管理的飞书应用，配置应用身份并完成用户 OAuth；密钥与刷新凭据保存到系统 keyring。只用于验证本地方案和真实文档读取，不能把它宣传为所有用户免配置授权。
2. **面向其他用户的发布门槛**：验证该应用类型是否支持无公共客户端密钥分发的桌面授权方案，以及回调/设备授权方式、刷新规则、个人空间支持情况。若支持，在 RiLL 内实现“连接飞书”。
3. 如果实际平台要求服务端保管公共应用密钥，则“所有用户免建应用”与“完全无后端”存在产品约束冲突；应在连接验证报告中给出结论。无后端首版可保留“使用自己的应用”高级连接方式，不能把公共密钥塞进安装包解决。

凭据不写入普通 SQLite 字段、日志、模型上下文或导出报告。刷新令牌轮换后更新 keyring；同账号并发刷新合并为一次。断开连接只清理凭据，不删除已经导入的本地投递。

HTTP 复用 `tauri-plugin-http`，限定飞书官方 API 目的地；不向用户粘贴的任意 URL 转发 Authorization。

Kimi-webbridge 等浏览器桥可以用于开发时核对页面。它与 RiLL 的正式连接是两件事：若未来要做浏览器扩展读取，需要独立定义用户安装、授权和结构化读取协议，本方案不假定现成桥已经接入 RiLL。

### 3.4 读取范围与完整性

- 优先定位链接指定的工作表/数据表；没有指定时展示可选列表。
- 链接带视图时展示“指定视图 / 整张数据表”的选择，默认优先尊重链接范围。若接口不能完整复现视图过滤、隐藏字段或记录权限，必须提示差异，不默默扩大读取范围。
- 首版一次处理一个选定的数据表；多个表可分别导入并各自保存映射。
- 分页一直读到 `has_more=false`，检查重复 `page_token`、重复 `record_id`、分页失败。
- Sheets 初始块可用 200 行；Base 初始页可用 100 条。它们是应用调优起点，不是平台最大限制。
- 每请求设置整体超时和取消信号；429 尊重 `Retry-After`，网络/5xx 有限退避，403 不反复重试。
- 达到本地配置的记录数或字节上限时显式终止/让用户缩小范围，不截断后报告导入成功。
- 分页期间结构改变则废弃映射结果并重读。无法获得一致快照时，记录“本次读取时间范围”，不承诺强一致快照。

## 4. 用户交互

### 4.1 首次导入

1. 求职中心的“从飞书导入”打开向导，粘贴链接。
2. 未连接时展示“连接飞书”；连接成功后显示文档名、数据表、读取范围。
3. 拉取结构和样例，展示自动映射；有多个合理候选的字段需要选择。
4. 用户可启用“AI 辅助识别”；说明将使用当前模型配置，仅发送相关字段及必要样例。无 AI 时可手动映射。
5. 生成全量预览，显示“可新增 / 已存在 / 内容变化 / 招聘信息 / 待核对 / 无效行”。
6. 用户修正字段、状态和行去向；默认不勾选覆盖已有记录和待核对项。
7. 点击“导入选中项”，提交冻结后的预览结果，返回真实提交统计。
8. 自动刷新投递列表，显示“查看新增投递 / 查看待投 / 查看待核对 / 撤销本次新增”。

### 4.2 再次导入

保存文档身份、结构指纹、映射版本、状态映射与范围设置。点击“一键导入新增”后：

- 结构和状态配置未变：复用映射；新增且无歧义的行可按保存设置提交。
- 相同行：跳过，不发给 AI，不增加记录。
- 有源更新、身份匹配不确定或本地修改：进入变更预览。
- 字段改名/删列/类型改变，或已映射的 RiLL 状态被删除：暂停受影响项，要求修正映射。

### 4.3 预览行必须展示的信息

公司、岗位、目标位置、源状态、RiLL 状态、投递日期、链接，以及问题提示。展开后可看原始字段、阶段历史、识别依据和来源定位。

“导入”按钮旁展示确定数量，例如“导入 23 条投递、8 条待投；12 条招聘信息未选；4 条待核对”。提交后不能把跳过或读取失败的记录算成成功。

## 5. 数据合同与标准字段

统一中间模型，飞书读取器只输出数据，不自行写入投递表：

```ts
type RowKind = 'application' | 'preparing' | 'listing' | 'review' | 'invalid';

interface SourceDescriptor {
  connectionId: string;
  kind: 'sheets' | 'base' | 'embedded-base';
  documentToken: string;
  resolvedResourceToken: string;
  containerId: string;
  viewId: string | null;
  canonicalUrl: string;
}

interface NormalizedImportRow {
  sourceRowKey: string; // Base record_id；Sheets 本批行定位，不代表稳定身份
  sourceExternalId: string | null; // record_id 或经用户指定、校验唯一的 ID 列
  sourceFingerprint: string;
  kind: RowKind;
  company: string | null;
  position: string | null;
  statusId: string | null;
  stage: string | null;
  appliedAt: number | null; // 真实投递时间；未知为 null
  applicationUrl: string | null;
  notes: string | null;
  extras: Record<string, unknown>;
  evidence: Array<{ fieldKey: string; sourceText: string }>;
  warnings: string[];
  raw: unknown;
}
```

字段策略：

| 标准含义 | 常见源字段 | 处理 |
|---|---|---|
| 公司 | 公司、企业、投递单位、company | 去首尾空白；不要盲目去掉公司后缀并用于自动合并 |
| 岗位 | 职位、申请岗位、方向、position | 部门可按映射拼接；保存完整岗位名，不使用显示截断值去重 |
| 个人状态 | 当前进展、申请状态、结果 | 结合列含义映射状态 ID；招聘开放状态不等于个人状态 |
| 阶段 | 网申、测评、笔试、一面、二面 | 保留详细阶段；按当前用户状态表映射 |
| 投递时间 | 网申日期、提交日期、申请时间 | 区别于发布时间、面试时间、截止日期 |
| 招聘链接 | 职位详情、网申入口、官网 | 保留真实 href；只有显示文字时不编造 URL |
| 备注与扩展 | 城市、薪资、内推码、联系人、评价 | 结构化保留；用户笔记不被反复拼接相同文本 |

正式写入投递记录至少需要公司和岗位。缺岗位时可由用户批量填写；不自动生成“未知岗位”填满列表。单元格中多个岗位只有在用户选择拆分、且能保留各岗位归属时才拆成多条；否则保留原文待确认。

## 6. 字段映射与逐行识别

### 6.1 两阶段映射

**结构识别**：读取字段 ID、名称、类型或 Sheets 表头与合并信息，识别标题行、表头行、重复表头、空行、说明行。允许用户手动指定表头行和数据起始行。

**语义映射**：先使用别名字典与类型约束，再用有限样例消除歧义；仍不确定时让用户选择。允许一列映射一个字段、多列合成一个字段；不允许一个不明确的“时间”列同时当投递和截止日期。

Base 使用 field ID 保存映射；Sheets 使用列位置与表头路径，结构指纹包含列顺序和合并表头，列重排后重新核对。Base 仅显示顺序改变可继续按 ID 匹配；类型和映射字段变化仍要重新核对。

不得因为公司列出现空格就盲目向下填充。只有真实合并区域或用户确认的分组规则可继承公司名称；继承动作写入识别依据。

### 6.2 分类规则

| 内容 | 分类与动作 |
|---|---|
| 个人状态“已投递/网申已提交”，或明确的个人投递日期 | `application`，映射为对应已投状态 |
| 个人阶段“笔试中/一面待安排/二面进行中” | `application`，匹配当前状态或进入状态映射，不默认把笔试当面试 |
| 个人结果“已拿到 Offer/被拒/本人放弃” | `application`；区分被拒与本人拒绝，不能无依据混为同一结果 |
| 个人意向“想投/准备投递/未投” | `preparing`，状态为明确的 preparing ID |
| 招聘链接、招聘岗位、招聘截止等，没有个人进度 | `listing`，首版默认不写已投记录，可由用户选入待投 |
| “状态：开放/已截止” | 招聘开放状态，不能当个人通过/失败 |
| “招聘流程：笔试→面试” | 招聘说明，不能当个人已经参加笔试或面试 |
| “结束/通过/待处理”、只有颜色含义、相互冲突的信息 | `review`，要求核对 |
| 标题、合计、重复表头、纯空行 | 非业务行，记录跳过原因；缺必要字段的业务行进入修正区 |

### 6.3 多列进度与日期

- 阶段列中填日期表示“计划/已发生”需要结合表头与用户规则；未来面试日期不等于面试已完成。
- “通过一面”不直接等于“二面进行中”；“收到测评”不直接等于“测评已完成”。
- 多列矛盾或无可信时间顺序时，不简单选最右列或最高阶段。
- 年份缺失、`3/4` 等歧义日期需要使用用户确认的源表年份/日期格式；不能按导入当天猜年份。
- Base 时间戳、Sheets 日期序列与文本日期分别解码；日期按应用当前单时区约定处理，保留源值和精度。
- “待通知/招满为止”保留原文，不解析成现在。截止时间、面试时间和导入时间不得代替投递时间。

### 6.4 AI 的职责与约束

AI 只参与字段映射建议和有歧义行的提取，不拥有数据库写工具。采用 Zod 验证结构化输出，严格校验字段 key、源行 key、可用状态 ID、URL 与日期。

每项识别保留原文依据；模型返回的置信度只用于排序提示，不能单独决定是否自动导入。不存在于源表且无用户补充的公司、岗位、日期与链接必须拒绝。

初始每批处理约 30～50 行，按字符/token 预算自适应拆批。来源内容视为数据，不执行其中要求调用工具或修改系统规则的文本。记录模型配置标识、解析版本和结构指纹；同内容不重复分析。源表变化重新验证，不能按“曾识别过”永久跳过。

模型超时、非法 JSON 或某行无法识别时保留进度，允许重试该批或切换手工；不把失败批标记为全部识别成功。提交阶段只用已经保存的预览快照，不再调用模型。

## 7. 本地存储与兼容迁移

### 7.1 投递表追加字段

保持既有 `job_applications` 和历史迁移内容不动。建议追加：

| 字段 | 用途 |
|---|---|
| `applied_at_known INTEGER NOT NULL DEFAULT 1` | 兼容原有 NOT NULL 列，表达真实投递日期是否已知 |
| `revision INTEGER NOT NULL DEFAULT 0` | 乐观并发控制和撤销保护 |
| `extras_json TEXT` | 保留结构化扩展字段与阶段信息 |

新导入的未知日期使用底层 `applied_at=0, applied_at_known=0`，service 统一映射为 `number | null`；不是向用户展示 1970 年。所有新增读写经 service，禁止 UI 直接理解底层占位值。

旧记录保留原有时间解释，不声称迁移能还原历史真实投递日期。旧待投记录不计入实际已投数量；后续点击“已投递”时写当前真实投递时间。

明确合同：`NewJobInput.appliedAt?: number | null`；导入输入必须显式提供 `number | null`，不能遗漏后触发旧默认值。`JobPatch` 增加 `appliedAt`。未知日期排序永远放最后，不随升降序跑到最前；未知日期不计入“近七天投递”。

`updateJob()` 改成单条参数化更新，避免一次编辑拆成多次字段更新。所有编辑、状态重分配和原生导入都递增 revision；真实投递时间由明确动作决定。

### 7.2 导入相关表

| 表 | 关键内容 |
|---|---|
| `job_import_sources` | 连接引用、真实资源类型/token、container、规范链接、文档名；保存数据源身份 |
| `job_import_mappings` | source ID、schema 指纹、解析版本、状态配置指纹、字段映射、阶段规则、默认去向 |
| `job_import_batches` | source ID、范围、状态、快照指纹、映射版本、计数、错误摘要、开始/结束时间、提交幂等 key |
| `job_import_rows` | batch ID、源行定位、稳定外部 ID（如有）、原始行、标准行、分类、预览动作、错误、目标 ID、提交前后快照 |
| `job_import_bindings` | source ID + 稳定外部 ID/确认过的业务身份 → job ID；上次源快照、上次写入值、目标 revision、删除/忽略标记 |

关键约束：

- 数据源身份包含连接身份、真实资源、container；视图属于读取范围，不属于 Base 同一记录的身份，避免换视图产生重复记录。
- `job_import_rows` 按 `(batch_id, source_row_key)` 唯一；bindings 对同一源身份加唯一约束。
- `job_import_batches` 的提交幂等 key 唯一；预览、确认、重试都围绕同一个批次。
- 目标被用户删除后，保留 binding，重新导入显示“本地已删除，是否恢复”，不自动重建。
- 删除来源连接与删除本地投递是独立动作；原始数据和历史可由用户清理，凭据不混入这些表。
- 来源记录的保存数量/保留策略可配置；清理快照后撤销入口相应失效，不能显示还能撤销。

迁移建议拆成 jobs 的连续追加项：导入表、日期标记、revision、extras。每个 ALTER 有独立 `skipIf`，迁移前做本地备份；在空库、存量库与中断后重放三种场景验证。最终编号按实施时的 `index.ts` 末尾计算。

## 8. 去重、更新与撤销

### 8.1 身份与内容分开

- `source identity`：用于识别“仍是同一条源记录”。
- `source fingerprint`：用于判断“这条记录内容有没有变化”。
- `business identity`：用于发现已有手动记录或不同来源的疑似同一岗位。

Base 优先使用真正的 record ID；Sheets 使用用户指定且唯一的编号列。没有稳定编号时，使用公司 + 完整岗位 + 批次 + 地点 + 职位级链接生成候选业务键，必须区分“相似”与“确定相同”。

行号只能用于定位，不能作为持久去重 ID；不能把全行哈希当稳定身份；不能只凭公司主页 URL 合并多个岗位；不能用截断的岗位文字合并。

Sheets 修改了参与业务键的字段、或同公司同岗位重复申请时，身份匹配可能不确定。这些情况进入待核对，不宣称无稳定编号也能百分之百跟踪每一行。

### 8.2 再次导入策略

1. 相同源身份、相同内容：跳过。
2. 相同源身份、源内容改变：生成更新候选，不新增第二条。
3. 命中手动或其他来源记录：预览“关联已有 / 新建独立申请”，不自动合并跨来源记录。
4. 导入中出现重复源身份或业务候选冲突：进入核对，保留每条原文。
5. 源记录未出现在本次视图/范围：不判定已删除，不删除本地。

更新采用三方比较：上次导入写入值、当前 RiLL 值、本次源值。默认模式只新增，不覆盖；用户选择“同步源变化”后，才按字段展示补充与冲突。

即使源表的状态看起来“更早”，也不建立简单线性等级强制前进/后退；投递流程可能重启。用户改过的状态、备注和日期默认保护；空源值不默认清空本地值。

### 8.3 原子提交与重试

本地 JS SQL 插件没有公开可跨多次调用固定连接的事务句柄，不通过 `db.execute('BEGIN')` + 若干调用 + `COMMIT` 假装实现可靠事务。

新增窄接口原生命令 `jobs_import_commit`：接收批次 ID、预览版本/哈希、选中行与允许的动作；在应用固定数据库上开启同一连接事务。不得接收任意数据库路径或任意 SQL。

优先复用 SQL 插件暴露的 Rust 数据库池；若无法稳定访问，使用匹配现有 lockfile 的 SQLx（当前为 0.8.6）连接同一个 `appDataDir/riliagent.db`。必须验证路径一致，避免创建一个 UI 看不到的新库。设置有限 busy timeout，并测试与现有窗口写操作的并发。

事务内重读批次状态、必要字段、目标 revision 与唯一绑定，验证提交动作；写入投递、扩展信息、来源绑定、逐行审计和批次完成状态后一起提交。任何数据库失败整批回滚。

TS 负责识别与业务预览，Rust 只承担受限的原子持久化和必要的二次验证。这个 Rust 增量是针对前端 SQL 能力的明确补足，不能假定“纯 TypeScript”同时免费获得可靠多表事务。

预览期间本地 revision 或状态配置变化时，中止并要求刷新受影响预览。相同批次并发确认、双击按钮和响应丢失后的重试，返回同一个提交结果。取消发生在事务提交前则回滚；提交后取消显示“已经完成”，不得报告为未导入。

读取不完整的批次不得默认提交。用户如明确选择导入已读取的部分，另建范围明确的新批次，结果显示部分范围，不把它当原范围完整成功。

批次状态机建议为 `reading → mapping → analyzing → ready → committed`，另有 `failed / canceled / undone / partially_undone`。提交期间使用原生锁与事务防止并发，不将前端“按钮已禁用”当作唯一保护。可重试错误保留阶段检查点，结构或映射变更则使后续结果失效；提交与撤销后的批次不得退回 ready。撤销后再次导入必须生成新批次，旧确认请求仅返回原批次当前状态，不重放写入。

### 8.4 撤销

首版提供“撤销本次新增”：仅移除这个批次创建、且提交后未被编辑/被后续导入修改的记录；发生 revision 变化的记录列为不能自动撤销，保留现状。来源关联与批次日志同步处理，不能留下“记录已删、来源仍认为已导入”的错误状态。

本批次对旧记录做了更新时，使用提交前后快照生成逐条恢复预览；仅当当前值仍等于本批次写入结果时才允许恢复，不覆盖后续人工编辑。不提供无条件整批删除式撤销。

## 10. 错误处理与可观测性

| 情况 | 用户反馈与动作 |
|---|---|
| 链接格式不支持 | 展示支持类型，不发无意义网络请求 |
| 未连接/凭据过期 | 引导连接；允许保存链接继续，不丢向导内容 |
| 应用权限不足、用户无权、跨租户限制 | 区分原因和能采取的动作，不能笼统显示“网络错误” |
| 内嵌表无法解析 | 明确标明该类型尚未支持；导出文件仅为替代路径，不算链接功能验收通过 |
| 超链接仅取到标题 | 提示该字段未获得真实地址，允许空值，禁止编造 |
| 分页/限流/网络失败 | 有限重试，记录读取游标；读取完整前不能自动进入提交 |
| AI 失败或未配置 | 保留规则结果，手动修正或仅重试失败批 |
| 状态/结构变化 | 标记映射失效，定位需要重新选择的字段 |
| SQLite 忙/磁盘不足/中断 | 原子回滚；保留可重试批次，明确没有正式提交 |
| 本地记录发生变化 | 提示预览过期，重新计算差异 |

阶段进度使用“正在连接 / 读取 300 条 / 识别 280 条 / 等待核对 / 提交中”，不要凭 API 总行数猜百分比。记录批次 ID、阶段耗时、请求数量、读取条数、识别错误码；不记录完整凭据、授权码和含私人内容的完整响应到普通日志。

大表预览分页或虚拟化；不一次渲染数千行。原始行保存在本地 staging，AI 只接收执行该步骤需要的数据。模型成本提供估算和处理上限。

## 11. 测试与验收

新增测试应针对真实风险，不测试 JSX 是否包含按钮这类实现镜像。当前项目没有统一测试脚本，可为本功能引入精简的 Vitest 纯函数测试；Rust 用数据库事务集成测试。测试库版本按实施时 Vite/TypeScript 兼容性选定。

| 编号 | 场景 | 必须得到的结果 |
|---|---|---|
| A01 | 本文示例的已授权真实飞书链接 | 确认数据模型并读到字段与全范围记录；不是只拿页面标题 |
| A02 | 普通 Sheets、独立 Base、内嵌记录表 | 各使用验证过的读取器；不凭 URL 路径误判 |
| A03 | 未登录、过期、403、个人空间不支持 | 清楚区分原因；不写正式投递 |
| A04 | table/view 参数与全表范围 | 预览范围准确；不能意外导入其他表或隐藏范围 |
| A05 | 两个人表头不同、顺序不同 | 正确映射；手动修正后再次导入可复用 |
| A06 | 多行表头、标题说明、重复表头、合并公司 | 有效行准确；不盲目向下填充 |
| A07 | 同表混合招聘、待投、已投、面试 | 分类正确；招聘清单不变成已投记录 |
| A08 | “招聘流程含面试”“状态已截止” | 不误判为用户个人面试或被拒 |
| A09 | 网申/笔试/多轮面试分列、有未来安排 | 综合解释，保留阶段；冲突进入待核对 |
| A10 | 复选框、日期、数字、多选和链接对象 | 不丢字段类型，保留真实 href |
| A11 | 未知日期、缺年日期、截止日期 | 不生成今天；未知日期置底且不计近七天投递 |
| A12 | 用户自定义状态、导入期间删除状态 | 只写有效 ID；变化后预览失效 |
| A13 | 连续导入两次、双击、响应丢失后重试 | 只有一份记录和一份提交结果 |
| A14 | Sheets 行排序、插行，Base 切换视图 | 稳定 ID 不重复；无稳定 ID 的歧义项待核对 |

| A17 | 源表更新，本地已改备注/状态 | 三方差异准确，保护本地修改 |
| A18 | 本地删除后再次导入、源表删行 | 不自动恢复本地删除，不自动删除本地记录 |
| A19 | 分页 >500 条、429、超时、重复游标 | 全量读取或明确失败；不静默截断 |
| A20 | AI 非法 JSON、乱造字段、源文含指令 | 校验拒绝；规则与手动路径仍可用 |
| A21 | 原子提交第 N 条失败、磁盘错误 | 正式投递和来源绑定均不留下半批数据 |
| A22 | 预览后另一个窗口编辑、同时确认 | revision 检测生效；不丢人工编辑 |
| A23 | 取消读取、取消识别、提交时取消 | 各阶段结果准确；提交后的成功不报告为取消 |
| A24 | 撤销新增，之后有人工编辑/再次导入 | 仅撤销未变记录，有后续变更的留待核对 |
| A25 | 投递日期为空后手工补录、待投转已投 | 保存成功、日期和统计正确、页面即时刷新 |
| A26 | 空库、旧库、ALTER 后迁移中断重启 | 迁移可重放，不改历史迁移 ID、不丢旧记录 |
| A27 | 数据完全相同但列改名/状态配置改变 | 对受影响映射重新核对，不错误使用过期规则 |

完成实现后的检查：前端 `npm run build`、本功能测试、原生编译/事务测试、Windows 真机授权与导入；若宣称支持 macOS，还须完成相应 keyring、回调和提交验证。

业务验收必须包含用户自己的实际链接。仅用本地 JSON fixture、Excel 替代导入或浏览器页面截图，不能证明“给飞书链接就能导入”已经完成。

## 12. 实施顺序与工作量

以下是单人熟悉该仓库、具备开发环境后的初步工程估算，不是执行承诺；授权审批、平台限制、个人空间和内嵌表不支持可能改变工期。

| 阶段 | 工作 | 退出条件 | 估算 |
|---|---|---|---|
| P0：连接与真实数据验证 | 核实授权、个人空间、示例内嵌表、字段和视图；保存脱敏 fixtures | 实际链接可读；明确发布版授权方式和限制；否则先解决连接问题 | 1～2 天 |
| P1：标准化与识别 | 数据合同、类型读取、映射、日期、阶段、分类、AI 可选路径 | A05～A12、A20 的针对性测试通过 | 2～3 天 |
| P2：导入持久化 | 兼容迁移、批次、绑定、去重、revision、原子提交、重试 | 同批幂等、故障回滚、旧库升级验证通过 | 2～3 天 |
| P3：产品流程 | 入口、向导、字段调整、预览、结果、刷新、撤销新增 | 用户可不经过聊天完成一次真实导入 | 2～3 天 |
| P4：联调与交付 | 多结构表格、分页、权限失败、取消、冲突、真机 | 验收矩阵通过，限制写入说明 | 1～2 天 |

首版约 8～13 个开发日；可先交付“已授权链接 + 手动映射 + 预览 + 幂等新增”的纵向小版本，再补 AI 与复杂阶段判断。不能为赶界面进度跳过 P0，或以 Excel 导入替代真实链接验收。

推荐提交顺序：连接技术验证报告 → 数据合同和纯函数 → 迁移与日期兼容 → 原子提交和去重 → 向导与刷新 → AI 辅助 → 联调与说明。每步构建通过，避免把新功能与当前工作区已有主题/排版修改混在一次提交中。

## 13. 关键决策与开放问题

已经确定：

- 主入口在求职中心，正式目标是现有投递表。
- 不强迫用户统一表头；映射按来源保存，修改结构后重新核对。
- 分类按行，规则优先、AI 可选，写库通过冻结预览与校验。
- 未知日期不补今天；个人进度不从招聘流程文字推断。
- 首版默认新增，覆盖需要明确选择；重复点击和重试幂等。
- 用追加迁移适配既有数据，通过原生命令补足事务能力。
- 不依赖用户安装开发者使用的 Kimi/Codex 浏览器工具。

必须在 P0 回答，当前尚无事实支持直接定案：

1. 该 `my.feishu.cn` 文档的实际数据模型和可调用的读取接口是什么？
2. 当前用户身份、应用类型和只读权限能否访问这份个人空间文档？
3. 内嵌表如何获得经官方接口验证的资源身份？指定视图的过滤是否可完整复现？
4. RiLL 发布版能否在完全无后端的前提下提供面向普通用户的一次连接流程？
5. 实际表格是否有稳定编号、复选框含义和多阶段日期约定？

这些是需要验证的技术事实，不应被模型猜测或示例字段替代。P0 完成后，将真实响应的脱敏样例、已验证 API、授权步骤、支持范围和剩余限制补入本文件的附录。
